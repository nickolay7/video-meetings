# План: Профиль пользователя

**PRD:** [user-profile.md](./user-profile.md)
**Дата:** 2026-08-05

## Фаза 1: Backend — поле `name`, получение и обновление профиля

**Цель:** регистрация принимает необязательное имя; авторизованный пользователь может получить свой профиль и изменить имя. Без JWT — 401.

**Затрагивает:** `backend`, `test`

**Задачи:**

1. Добавить необязательное поле `name` в сущность `User` и провести его через регистрацию (DTO/команды); регистрация без имени допустима, при отображении вместо имени используется email.
2. `GET /profile` (JWT) — возвращает id, имя, email; поле аватара добавится в фазе 2.
3. `PATCH /profile` — обновление имени; пустое имя допустимо (устанавливается «не задано», при отображении — email).
4. e2e-тесты: регистрация с именем и без, получение профиля, обновление имени (включая очистку), 401 без токена.

**Критерий готовности:** профиль можно получить и изменить имя через API; регистрация работает с именем и без него; e2e-тесты зелёные; без токена — 401 (критерии PRD 1–3, часть 9).

## Фаза 2: Backend — аватар и смена пароля

**Цель:** пользователь может загрузить и получить свой аватар (изображение, до 5 МБ) и сменить пароль, подтвердив старый.

**Затрагивает:** `backend`, `test`

**Задачи:**

1. `POST /profile/avatar` (JWT, multipart) — приём аватара: валидация типа по фактическому содержимому (изображение), лимит 5 МБ (413 при превышении); сохранение на диск в `uploads/avatars/<userId>/` с контролируемым именем хранилища (не пользовательским путём); повторная загрузка заменяет прежний файл.
2. `GET /profile/avatar` — выдача аватара текущего пользователя; 404, если аватар не загружен.
3. `POST /profile/password` — смена пароля: старый пароль проверяется (bcrypt); при неверном старом — понятная ошибка, пароль не меняется; при верном — новый пароль валидируется (минимальная длина) и сохраняется хешированным.
4. Задокументировать поведение после перезапуска: пользователи in-memory сбрасываются, осиротевшие аватары на диске игнорируются (по образцу файлов встреч).
5. e2e-тесты: загрузка аватара (включая отказ при не-изображении, файле >5 МБ и 401), выдача аватара, смена пароля (включая неверный старый и вход новым паролем).

**Критерий готовности:** аватар загружается, заменяется и отдаётся; лимиты типа и размера работают; смена пароля проходит только с верным старым; e2e-тесты зелёные (критерии PRD 4, 5, 7, 8, оставшаяся часть 9).

## Фаза 3: Frontend — страницы `/profile` и `/profile/edit`

**Цель:** пользователь может посмотреть свой профиль и отредактировать его: имя, аватар, пароль.

**Затрагивает:** `frontend`

**Задачи:**

1. Необязательное поле «Имя» в форме регистрации; при пустом — регистрация без имени.
2. Страница `/profile`: просмотр аватара, имени (или email как fallback) и email; ссылка на редактирование.
3. Страница `/profile/edit`: форма изменения имени (очистка поля → при отображении используется email), загрузка аватара с превью и заменой, форма смены пароля (старый + новый).
4. Обработка ошибок: неверный старый пароль, файл не-изображение или больше 5 МБ — понятные сообщения; при ошибке аватара прежний аватар не теряется.
5. Визуальная проверка обеих страниц через Playwright MCP (критерий 10 PRD).

**Критерий готовности:** с `/profile` виден профиль и есть переход к редактированию; с `/profile/edit` меняются имя, аватар и пароль; ошибки отображаются понятно; UI проверен визуально (критерии PRD 3, 5, 7, 8 на уровне интерфейса, часть 6, 10).

## Фаза 4: Frontend — шапка главной: аватар и имя пользователя

**Цель:** после входа пользователь видит свой аватар и имя (или email) в шапке главной страницы.

**Затрагивает:** `frontend`

**Задачи:**

1. На главной странице загружать профиль и отображать аватар в шапке вместо статичных инициалов; имя (или email как fallback) — в приветствии.
2. Ссылка на `/profile` из шапки.
3. Актуальность данных: после изменения имени/аватара на `/profile/edit` главная показывает обновлённые значения (без ручного обновления).
4. Визуальная проверка шапки через Playwright MCP (критерий 10 PRD).

**Критерий готовности:** в шапке главной отображаются аватар и имя/email пользователя; имя и аватар на главной обновляются после правок в профиле; UI проверен визуально (критерии PRD 3, 6, 10).
