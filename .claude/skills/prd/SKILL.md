# PRD Generator Skill

## Метаданные

- **name**: `prd`
- **description**: создаёт PRD-документ для фичи по стандартной структуре проекта; используется, когда нужно описать требования к новой фиче перед реализацией.

## Поведение скилла

Скилл принимает аргумент — название или описание фичи — и на его основе создаёт PRD.
Файл сохраняется в папку `docs`; если папки нет, она создаётся автоматически.
Имя файла формируется автоматически: название переводится на английский язык и приводится к формату `kebab-case` (например, `file-upload.md`).

---

## Структура PRD-документа

Документ состоит из следующих разделов:

### 1. Заголовок и метаданные

- Название фичи
- Текущая дата (для датирования документа)
- Статус: `draft`

### 2. Цель

1–2 предложения: что нужно пользователю и зачем. Описывает итоговую ценность фичи, а не способ её реализации.

### 3. Пользовательские сценарии

Каждый сценарий строится по схеме:

- **Пользователь** — кто совершает действие
- **Действие** — что он делает
- **Результат** — что происходит в итоге

**Пример:**

> Пользователь заходит в раздел загрузки файлов → выбирает файл → файл загружается и отображается в интерфейсе.

### 4. Скоуп (область фичи)

- **Что в скоупе** — конкретный список того, что входит в данную итерацию.
- **Что не в скоупе** — явный список того, что не реализуется в этой итерации (например: не разрабатываем собственное хранилище, используем хранение на диске).

Этот раздел критически важен для предотвращения неконтролируемого расширения фичи.

### 5. Технические ограничения

Известные ограничения, которые необходимо учитывать.
Пример: развёртывание на сервере с ограниченными ресурсами.

### 6. Критерии готовности

Список проверяемых условий, при выполнении которых фича считается реализованной.
Критерии должны быть **конкретными** и **легко проверяемыми** — не абстрактными нагрузочными сценариями, а чёткими утверждениями, которые можно подтвердить или опровергнуть.

---

## Правила, заданные скиллу

Чтобы контролировать качество генерируемого документа, скиллу задаются явные ограничения:

- Писать конкретно, без «воды».
- Не описывать, _как_ реализовывать — только _что_ и _зачем_.
- Критерии готовности должны быть проверяемы.
- Если описание фичи недостаточно полное — задавать уточняющие вопросы до создания файла.

---

## Зачем нужен PRD

Абстрактная формулировка («хочу, чтобы файл загружался») не даёт команде достаточно информации для работы.
Скилл превращает такое описание в структурированный документ, который отвечает на вопросы:

- Какой именно пользовательский сценарий?
- Что входит в фичу, а что нет?
- Какие есть ограничения?
- По каким критериям принять работу?

Документ остаётся полезным на протяжении всего цикла разработки: при планировании, реализации и последующем изучении фичи другими членами команды.
